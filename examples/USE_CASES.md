## 1. 特許 — 長文アブストラクトの自動分類と要約

### 現場の悩み

毎月何千件と公開される特許のスクリーニングに、担当者が多大な時間を奪われている。

### プロンプト例

```
提供された特許の要約文（text）を分析し、以下のJSON構造を出力してください。
category: 技術カテゴリ（AI, IoT, 医療機器, 素材, モビリティ, 環境, その他）から最も適切なものを判定。
short_summary: 発明の核心となる解決手段と効果を、30文字以内の端的な日本語で要約。
```

### 期待される出力例

```json
{
  "category": "AI",
  "short_summary": "テキスト感情分析による購買意欲の予測モデル"
}
```

## 2. 医療 — 詳細な電子カルテテキストの構造化

### 現場の悩み

医師のメモや営業の自由記述テキストから、必要なデータをシステム（DB）に転記する作業が発生している。

### プロンプト例

```
提供された医師の診察メモ（note）を分析し、以下のJSON構造を出力してください。
symptoms: 患者の訴えや確認された症状を文字列の配列として抽出。
diagnosis: 確定診断名、または最も疑わしい病名を抽出（1つの文字列）。
treatment: 実施された処置、指示、または処方された薬剤名を文字列の配列として抽出。
```

### 期待される出力例

```json
{
  "symptoms": ["発熱", "咽頭痛", "嚥下困難"],
  "diagnosis": "急性化膿性扁桃炎（溶連菌感染症）",
  "treatment": [
    "アモキシシリンカプセル処方",
    "ロキソプロフェンナトリウム処方",
    "安静と水分補給の指示"
  ]
}
```

> 詳細な臨床ノートを使った実機の抽出例は、README の Quick Example を参照してください。

## 3. 金融 — アナリストレポート・決算短信のセンチメント分析と構造化

### 現場の悩み

毎日膨大なニュースやレポートを読み込み、自社のポートフォリオへの影響を評価している。

### プロンプト例

```
提供された金融・経済ニューステキスト（text）を分析し、以下のJSON構造を出力してください。
sentiment: 記事の内容が該当企業にとって "Positive"、"Negative"、"Neutral" のいずれであるか判定。
company: 記事の主語となっている対象企業名（1社）。
key_factor: そのセンチメント判定の根拠となる最も重要な要素（数値・事実）を、30文字以内で抽出。
```

### 期待される出力例

```json
{
  "sentiment": "Negative",
  "company": "C自動車",
  "key_factor": "半導体不足と洪水による3工場停止と5万台減産"
}
```

## 4. 法務・コンプライアンス — 契約書のリスク判定と条件抽出

### 現場の悩み

毎日送られてくる多種多様な契約書（NDA、業務委託など）の一次レビューに法務部が疲弊している。自社に不利な条項のチェック漏れを防ぎたい。

### プロンプト例

```
提供された契約書の条文テキスト（text）を分析し、以下のJSON構造を出力してください。
contract_type: 契約類型（秘密保持契約、業務委託契約、利用規約、その他のいずれか）を判定。
risk_level: 自社（受領側）にとってのリスクレベルを "High", "Medium", "Low" で判定。損害賠償上限の欠如や、非現実的な違約金、不当な解除条件があればHighとする。
special_notes: リスクの根拠となる要注意な条件を30文字以内で抽出。
```

### 期待される出力例

```json
{
  "contract_type": "業務委託契約",
  "risk_level": "High",
  "special_notes": "無催告解除時の1000万円の即座違約金支払義務"
}
```

## 5. カスタマーサポート — VOC（顧客の声）の構造化と分析

### 現場の悩み

コールセンターやお問い合わせフォームに長文で届く顧客の声を目視で読み解き、「クレーム」「要望」の仕分けや、製品別の課題集計を手作業で行っている。

### プロンプト例

```
カスタマーサポートに届いた顧客のメッセージ（log）を分析し、以下のJSON構造を出力してください。
inquiry_type: 問い合わせ種別（クレーム, 質問, 要望, 解約, 感謝）から1つ判定。
product_feature: 対象となっている製品名や機能名（例：ログイン画面、バッテリー、配送など）を抽出。不明な場合は null。
customer_emotion: テキストから読み取れる顧客の感情（激怒, 不満, 困惑, 中立, 好意的）を判定。
request_summary: 顧客が最終的に求めていること、または主張の核心を30文字以内で要約。
```

### 期待される出力例

```json
{
  "inquiry_type": "クレーム",
  "product_feature": "ロボット掃除機（RX-900）",
  "customer_emotion": "激怒",
  "request_summary": "ラグに引っかかる初期不良に対する返品・返金の要求"
}
```

## 6. 人事・採用 — 職務経歴書のスキル抽出と要約

### 現場の悩み

エージェントから大量に送られてくるPDFやテキストの職務経歴書を読み、求めるスキルセットと合致しているかを見極めるのに採用担当の工数がかかりすぎている。

### プロンプト例

```
候補者の自己PR・職務経歴テキスト（resume）を分析し、以下のJSON構造を出力してください。
roles: 経験した主要な職種（例：バックエンドエンジニア、営業マネージャーなど）を配列で抽出。
skills: 言及されている具体的なスキルやツール（例：Java, AWS, Salesforce, TOEIC900など）を配列で抽出。
management_experience: チームマネジメントやリーダー経験の有無を boolean (true/false) で判定。
core_strength: この候補者の最も強力なアピールポイント（ビジネス上の貢献や技術的強み）を30文字以内で要約。
```

### 期待される出力例

```json
{
  "roles": ["バックエンドエンジニア", "開発リーダー"],
  "skills": ["Java", "Spring Boot", "Oracle"],
  "management_experience": true,
  "core_strength": "Javaバックエンド開発力と5名規模のチーム牽引経験"
}
```

## 7. 不動産・施設管理 — 現場の点検レポートの構造化

### 現場の悩み

現場の管理担当者がスマホで入力した「自由記述の点検テキスト」から、修繕が必要な箇所だけをExcelに抽出し、工務店への発注リストを作成する手間がかかっている。

### プロンプト例

```
現場担当者の物件視察・点検レポートテキスト（report）を分析し、以下のJSON構造を出力してください。
condition_status: 物件の総合的な状態を "良好", "要修繕", "危険" から1つ判定。早急な対応が必要な物理的ダメージがある場合は"危険"とする。
repair_targets: 物理的に修理・交換・清掃が必要な箇所や設備名（例：エアコン、網戸、給湯器など）を配列で抽出。不要な場合は空配列。
concerns: 現場特有の懸念事項や、報告者が最も伝えたいリスクを30文字以内で要約。
```

### 期待される出力例

```json
{
  "condition_status": "危険",
  "repair_targets": [
    "1階和室の畳",
    "屋根の雨漏り",
    "外壁のクラック",
    "庭の樹木"
  ],
  "concerns": "雨水侵入とシロアリ被害による倒壊リスク、越境クレーム"
}
```

## 8. EC・マーケティング — 商品レビューの多角的な感情分析

### 現場の悩み

ECサイトの大量のレビューから、「総合的に何点か（レーティング）」だけでなく、「何が褒められて、何が不満か」の要素を分解して商品開発にフィードバックしたい。

### プロンプト例

```
ECサイトの商品レビューテキスト（review）を分析し、以下のJSON構造を出力してください。
estimated_rating: レビューの内容から推測される5段階評価（1:最低 〜 5:最高）を数値で判定。
pros: 評価されているポジティブな要素・機能・特徴を配列で抽出。なければ空配列。
cons: 不満が述べられているネガティブな要素・課題を配列で抽出。なければ空配列。
decisive_factor: このユーザーがこの商品を買う決定打となった理由、または総合的な感想の核心を30文字以内で抽出。
```

### 期待される出力例

```json
{
  "estimated_rating": 4,
  "pros": ["ノイズキャンセリング性能", "低音の音質"],
  "cons": ["専用アプリの使いにくさ", "長時間着用時の耳の痛み"],
  "decisive_factor": "音とノイキャン性能は最高だがソフトが惜しい"
}
```

## 使い方のヒント

- **JSONL ファイル形式**: 入力は 1 行 1 レコードの JSONL ファイルです。各行の JSON 構造は自由で、プロンプトで参照するフィールド (`note`, `text`, `report` など) が含まれていれば OK です。例えば医療カルテのユースケースなら、各行は次のような形になります:
```jsonl
    {"note":"30代男性。主訴：発熱..."}
    {"note":"50代女性。主訴：血圧高値..."}
```
- **モデル選択**: 軽量なタスクなら Gemini 3 Flash Preview、精度が必要なら GPT-5.4 や Claude Sonnet 4.6 がおすすめです
- **プロンプトの調整**: example_output に具体的なサンプルを 1 つ載せておくと、抽出精度が安定します
- **失敗レコードの扱い**: バッチ処理の中で個別レコードが失敗した場合、出力 JSONL の該当行は予約キー `$error` を持つ JSON になります (例: `{"$error": {"code": "...", "message": "..."}}`)。正常行はユーザー定義のスキーマそのままなので、各行で `$error` キーの有無を見れば正常/失敗を分岐できます
